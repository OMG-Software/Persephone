Privacy policy

This policy tells you what data the Persephone project collects, what the Persephone app sends and stores, and where other parties process data. It describes the project as it is today.

Not ready for use. Persephone is in early development. Do not use it for real conversations.

Who this policy applies to

This policy applies to:

  • the Persephone desktop app for Windows, Linux and macOS;
  • the source repository, OMG-Software/Persephone on GitHub;
  • this website;
  • the release downloads that the project publishes on GitHub.

This policy does not apply to:

  • Matrix homeservers. You choose the homeserver that you sign in to. Its operator processes your account and your messages under their own policy.
  • GitHub. GitHub hosts the repository, the website and the downloads. GitHub processes data under the GitHub General Privacy Statement.

What the project collects

The app and the project collect no data about you on their own.

  • The app has no telemetry, no analytics and no usage statistics.
  • The app does not upload crash reports.
  • The app does not check for updates. You install a new version by hand.
  • The app contacts no server that the project operates. The project operates no such server.

The project receives only what you choose to send it: a public issue or pull request, or a private vulnerability report. The maintainers can read a private report, and GitHub stores it. Send only what the report needs (see Contact).

What the app sends, and to whom

The app connects to the homeserver that you choose at sign-in. The sign-in screen suggests https://matrix.org; you can enter a different server. The app accepts only https:// addresses. Every connection uses TLS 1.3 or later, with certificate checks. The app does not follow redirects and does not use a proxy that is set in the system.

Homeserver discovery contacts the server name you enter and checks the discovered homeserver. The sign-in page shows the discovered address before sign-in. Browser sign-in opens the homeserver's authentication provider in your browser and uses a loopback callback to complete authentication. That provider and browser have their own privacy policies. A configured profile SOCKS5 proxy applies to connections the core makes; it does not configure your external browser.

The homeserver receives what the Matrix protocol needs. This includes:

  • your user ID, your password at sign-in and the session's access token;
  • a new device for this sign-in, with the device name Persephone;
  • the rooms that you are in, and your room membership;
  • the messages that you send;
  • your device's public keys, and the room keys that the app sends, encrypted, to other devices;
  • the images that you send;
  • requests for each image that you choose to load.

If you set up a key backup or a recovery key, the homeserver also stores your encrypted room-key backup. Persephone does not do this automatically; you start it. The core can show a new recovery key and save it to a file you choose. Such an exported file remains outside the encrypted profile and needs your protection; it is not an automatic browser-storage copy.

The homeserver shares room data with the other servers whose users are in the room. The other people in a room receive your messages and can see your membership. This is how Matrix works, and the app cannot change it.

Starting a conversation

When you start a conversation, the app first looks for an encrypted room that you have joined, that is marked as a direct conversation with that person, and whose only members are the two of you (the person joined or invited). If it finds one, it opens it and sends no request to start a new one. Otherwise, the app needs the person's cross-signing identity. If the app does not have it yet, it sends the Matrix ID that you enter to your homeserver to ask for it. Only if the person has a cross-signing identity does the app ask the homeserver to create an encrypted room and to invite them. Having encryption keys without a cross-signing identity is not enough. The invitation also reaches the person's homeserver, as any Matrix invitation does.

Search for people is off each time you open the dialog. If you turn it on, the app sends what you type, without leading or trailing spaces, to your homeserver's user directory. It sends it 0.4 seconds after you stop typing, once it is at least two characters long. Your homeserver can keep a record of these searches. Results show names and Matrix IDs as text. The app fetches no avatars.

The public room browser sends nothing until you press Browse. Then the app asks your homeserver for one page of a public room directory, with the search text if you entered one. If you enter another server, your homeserver asks that server for its directory on your behalf; the app does not connect to it. Both servers can keep a record of these requests. Results show names, room addresses and topics as text. The app fetches no avatars. When you join a listed room, the room's members and servers see your Matrix ID. Public rooms are usually not encrypted.

When you accept a direct-message invitation, the app joins the room. When you decline it, the app leaves the room. Your homeserver and the person who invited you can see either answer.

What encryption protects

In an encrypted room, the app encrypts message content and images before it sends them. The homeserver cannot read that content.

Encryption does not hide all metadata. The homeserver, and other servers in the room, can still see who is in a room, who sends messages, when, and how large the messages and files are. Persephone does not make you anonymous and does not hide your traffic patterns.

In a room that is not encrypted, the homeserver can read your messages. The app labels such a room and asks you to confirm before you send the first message there. An encrypted send never falls back to plain text.

Ignoring users and reporting messages

The ignore list is Matrix account data stored on your homeserver. Its operator can read the user IDs on that list. Other clients for the same account can use it. Ignoring hides message content from those users in Persephone's timeline and local search. Room state events can still appear. Ignoring does not remove a user from a room, revoke their access, or withdraw keys already shared.

Reporting requires an explicit confirmation. The app sends the room ID, event ID and your required reason to your own homeserver. It does not attach the message body. The homeserver operator can read the reason even when the room is encrypted. Do not put message text or other private data in the reason unless you intend to disclose it. A report is not a promise of moderation.

Local message search

Message search reads only the SDK's existing encrypted local event cache. The query causes no HTTP request, history download, or room-key request. The app creates no separate search index. It searches only text already decrypted in that cache. Missing history, undecrypted events and resource limits mean the results do not cover all messages. User-directory search described above is a different operation and does send its query to your homeserver.

Search can also filter by exact sender and an inclusive start and exclusive end time. Dates use the original event timestamp, including when edits or redactions change the displayed text. Unknown dates do not match a date filter. The cache does not grow because of search, and the app creates no search index.

Room navigation and inspection

Jump to date sends the room ID and requested time to the homeserver. It does not send a search term. The core asks for the first event at or after that time, and tries the last event before that time only if the server returns 404. It then requests bounded event context. Attachment browsing requests room history in chunks of at most 50 raw events. Filters apply locally. The panel shows metadata; it does not load media automatically. You must choose an existing media action to fetch or open an attachment.

Pinned messages use standard m.room.pinned_events room state. This state is unencrypted room metadata, including in encrypted rooms. It contains event IDs, not message snippets. Room participants and the homeserver can see these IDs. A pin change requires the user's current room-state power level and reads fresh state first, but concurrent state writes have no compare-and-swap protection. The panel shows at most 100 IDs and refuses new pins at that limit. Removing a pin from a larger list preserves the other references within the core's separate state and request-size limits. See Room tools.

Connection health is a manual view of existing sync observations. It starts no probes or background tasks. Displayed timestamps use the computer clock and do not prove that the client is currently connected. Locking resets the health snapshot.

Images

  • Received images. The app shows a placeholder for each received image. It downloads the image only when you choose to load it. A download tells your homeserver that you opened the image. If the image came from another server, your homeserver can fetch it from that server.
  • Sent images. Before it sends an image, the app makes a copy without location data and other metadata, for example EXIF, XMP, comments and colour profiles. Of the metadata, the copy keeps only the orientation tag, so that the photo does not appear rotated. The pixels do not change. The app sends the copy with a generic file name, image.png or image.jpg, so the original file name does not leave your device. The app never changes your original file.

The app does not show link previews and does not load content from the web.

Calls

  • Who sees a call. A call uses your homeserver's call service (a LiveKit media server) and its relay (TURN) servers. They see who is in the call, when, your IP address, and the size and timing of the audio and video packets. They do not see the audio or the video: each sender encrypts its media with keys that only the call members get.
  • Proxy. Calls cannot use the profile's SOCKS5 proxy. When a proxy is set, the app asks before each call whether to connect directly.
  • Microphone. The app records from the microphone only during a call. Mute stops sending audio.
  • Camera. The app uses the camera only after you choose "Video call" or turn the camera on during a call. Turning the camera off stops it, and the camera light goes out. The app uses only the camera that you chose in Settings, or the first camera when you chose none. It never changes to another camera.
  • Devices. The app saves your choice of microphone, speaker and camera in the encrypted profile. Listing devices does not record, play or open a camera.

What the app stores on your device

The app keeps your account in a local profile. The profile holds the Matrix SDK's databases: account state, the message cache, the media cache and the encryption keys.

The profile also keeps per-room text drafts and their reply event references, favourites and named room sections. They use bounded encrypted records in the SDK crypto store. The app does not upload them as Matrix room tags or keep them in browser storage. Each profile has its own records. Draft text and search results are visible to the UI while it shows them; keeping keys in the core does not hide displayed content from a compromised UI.

Search itself sends no query or history request. Selecting a search result can request normal room history to locate that message. Saved drafts can remain after leaving a room. Use Saved drafts to view or discard those local records.

  • A random 32-byte key encrypts the values in these databases.
  • By default, the operating system's keystore alone protects that key. The profile then opens with no prompt. Anyone, and any program, that can use your computer account can open it.
  • You can turn on a profile passphrase in Settings, Security. It protects the key with a second layer, and the app asks for it each time it starts. You can turn it off again. The app has no way to recover a forgotten passphrase. Lock and the idle lock exist only while the passphrase is on.
  • The operating system's keystore protects the key in both cases. On Windows this is DPAPI. The Linux Secret Service adapter is not implemented. The macOS Keychain adapter is implemented but has no recorded native app run. If no keystore is available, the profile stays locked. The app never writes an unprotected key instead.

The app keeps images that you load in memory only. It drops them when you lock the profile or sign out.

The app does not keep your login password.

Diagnostic log

The app writes no log file unless you turn on the diagnostic log in Settings, Diagnostics. It is off each time the app starts. Before it starts, the app asks you in its own window. While it is on, the app writes one file, diagnostics/persephone.jsonl, in the profile's folder. Settings shows the full path.

The log holds what the app and its libraries report: your user ID, other users' IDs, room IDs, server names, device IDs, network addresses, and the type, sender, time and size of each Matrix event. The app's own records of events never hold message text, media or other event content. The libraries the app uses can put other text in their own records, and the app does not remove message text from that text. The app never writes passwords, access tokens, call tokens or keys to the log on purpose, and it filters such values out of library text. A filter cannot be complete, so read the file before you send it to anyone.

When you turn the log off, the file stays, so you can send it. Each profile has its own file. The next time the app starts with that profile, it writes random bytes over the file and then deletes it. The file of a profile that you do not start again stays on the disk until you do. On an SSD, and on some file systems, old copies of the data can stay on the disk where no application can reach them. The app cannot remove those copies.

Signing out and resetting

When you sign out, the app asks the homeserver to end the session. It then deletes the profile's key, so the remaining files cannot be read. The next time the app starts, it deletes the profile's files.

If you forget your passphrase, "Reset profile" deletes the profile without the passphrase. The new profile has no passphrase. The app cannot end the old session on the homeserver in this case. Remove the old device from another Matrix client.

Limits

  • The databases encrypt their values, not the whole files. Table names and some lookup keys stay visible.
  • Deleting a file does not erase it securely. Copies can remain on SSDs, in backups, in system snapshots or in swap space.
  • The app cannot protect data on a device that an attacker controls, or data that the other people in a room keep.
  • Components of the operating system, such as the system web view, can keep their own files. This policy does not describe them.

The website

GitHub Pages hosts this website. The website's pages:

  • set no cookies;
  • have no analytics, no scripts and no tracking;
  • load no fonts, images or other files from third parties;
  • tell your browser not to send a referrer when you follow a link.

GitHub can process technical data, such as your IP address, when you visit the website. See the GitHub General Privacy Statement.

Release downloads

The project publishes release downloads on GitHub Releases. GitHub can process technical data, such as your IP address, when you download a file.

Release signing transparency

The release workflow signs the SHA256SUMS file with Sigstore cosign, without a stored key, through the workflow's own identity. The signature is recorded in Sigstore's public transparency log. The record holds the identity of the release workflow (the repository, the workflow file and the release tag), not data about you. Each file also has a build-provenance attestation, made through the same workflow identity.

Children

Persephone is not made for children. The project collects no data from anyone, so it holds no data about children. Your homeserver can have its own age rules.

Changes to this policy

The policy is kept as PRIVACY.md in the project's git repository. Its history shows every change. Each version shows the date of its last update at the top.

Contact

To report a privacy or security problem privately, use GitHub's private vulnerability reporting. Only you and the project's maintainers can see the report. You need a GitHub account. The security policy says what to include.

Ask general questions about this policy in the repository's issue tracker. Issues are public. Do not put personal data, chat content or security details in an issue.
