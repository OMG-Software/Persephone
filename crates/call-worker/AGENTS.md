# Call worker

The contained process that runs one call (ADR-0043). It joins one LiveKit room with frame encryption and platform audio. It speaks the bounded protocol of `crates/call-protocol` over stdin and stdout.

- Treat the core's messages and the SFU as untrusted. Validate every identity before it goes back to the core. Send no free text, only closed `FailureCode` values. The one exception is `FromWorker::Diagnostic` (ADR-0058): `diagnostics.rs` sends `log` records and room event notes only while the core has sent `SetDiagnostics { on: true }`, at most 256 waiting, 200 a second and 8 per writer round after control messages and a waiting picture. `log` records take at most 192 waiting and 150 a second (`Source::Library`), so a libwebrtc flood never drops the room event notes (`Source::Note`). Never put a token, JWT, key or frame key in a note.
- Stdout is the frame channel. Write nothing else to it. Write nothing to stderr. Add no logging output other than the diagnostic records above.
- Keep the JWT, TURN credentials and frame keys in `Zeroizing` until they go to LiveKit. Move them out with `std::mem::take`; do not copy them. Never log them.
- Use bounded queues only. The LiveKit event receiver is unbounded inside the SDK; the worker drains it in one task.
- Check containment before reading any input. On a missing control send `Ready`, then `Failed(Containment)`, and exit. The feature `dev-uncontained` skips the exit for local tests only. Never enable it in a build that ships.
- A decryption failure of one remote participant does not end the call.
- Keep each LiveKit type inside `session.rs`. Keep `mapping.rs` and `video.rs` free of I/O and LiveKit types so they stay unit-testable.
- Camera and video (ADR-0048): `camera/mod.rs` is the platform-neutral API (`list`, `open`, `Capture`, `CapturedFrame`) with no OS or LiveKit types. New OS backends go in `camera/<os>.rs` behind the same API. Each one needs its own ADR and containment review. Do not add one without them.
- Windows camera: the open needs the `webcam` device capability SID that the broker adds (`CALL_DEVICE_CAPABILITIES`); without it `ActivateObject` fails with `E_ACCESSDENIED` (`docs/evidence/camera-windows.md`). `camera/windows.rs` notes each failed step and its HRESULT through `log` (`note`, `failed`, `missing`), never a device ID or name. Run the ignored camera test in `crates/core/src/platform/windows/call.rs` after a containment change.
- Screen sharing (ADR-0053, ADR-0064): `screen/mod.rs` is the platform-neutral API (`open`, `Capture`, `CapturedFrame`, `Ended`, `Grant`) with no OS or LiveKit types. Backends: `screen/linux.rs` (PipeWire over the ScreenCast portal remote of kind `s`, shared-memory buffers only, BGRx, RGBx, BGRA and RGBA); `screen/windows.rs` with `screen/frame_pipe.rs` (no capture of its own, ADR-0067 proposed: it reads the frames that the screen helper writes to a pipe, see below); and `screen/macos.rs` (ScreenCaptureKit through `objc2`, ADR-0064; one display, BGRA, at most 1920x1080 and 5 frames per second, no window left out; its pure rules are in `screen/display.rs` and run on every OS). Windows.Graphics.Capture and DXGI duplication fail with `E_ACCESSDENIED` in the call AppContainer (`docs/evidence/screen-share-windows.md`), so the worker does not capture the screen on Windows: `crates/screen-helper` does, outside the container, and its code (`wgc.rs`, `monitor.rs`) is not part of this crate any more. The GDI capture moved to the containment gate (`tests/platform/windows/src/gdi.rs`), which still measures what the container can do. Give the worker no capability and no relaxed mitigation for screen sharing, and remove no Win32k lockdown gap by accident: the worker still has no Win32k lockdown (its audio stack needs it), so it can still copy any monitor with GDI; ADR-0067 says so. On Windows the core names the monitor with `ScreenTarget::Monitor` (GDI device name, size in pixels and rectangle, call protocol version 12) and starts the helper for it; the worker only checks that frames arrive. `ToWorker::ScreenFrames { share, handle }` (before `SetScreen`) names the read end of the helper's frame pipe as a handle value inside the worker; `session.rs` keeps at most one (`screen_frames`), adopts it only when it is a pipe end (`GetFileType` and `GetNamedPipeInfo`, which refuses a socket), none of the worker's standard handles and none that the worker owns already (`frame_pipe::adopt`: a `FramePipe` lists its value from its adoption until its close, under one lock), never closes a handle that it refuses, and gives it to the start of that share only (`screen_grant`); another share's pipe stays for its own start or is dropped by the next `ScreenFrames`. `screen/windows.rs` hands pictures on at most once for each `PICTURE_GAP` (the screen limit and 20 ms, counted from the end of the last callback), so the feed's limiter never drops one, keeps the newest early one until it is due, and hands the newest on again every `REPEAT_GAP` (1 s) while the screen stays still, for the whole share, because the feed drops pictures until the track is published and a remote that subscribes later needs a new input picture (whether the encoder sends the last one again on its own was not measured); it reads into two buffers kept for the share (`read_item_into`). `frame_pipe::PipeReader` reads with `PeekNamedPipe` and short waits (never a blocking read; 5 ms inside an item, 25 ms between items), so a stop or a stalled or trickling helper cannot hold the capture thread: call `begin_item` before each item, which gives the whole item `STALL_TIMEOUT` (3 s). `screen/windows.rs` waits for the first item (at most 6 s to its first byte and `STALL_TIMEOUT` for the item, 1 s under the 10 s `OPEN_TIMEOUT` of `screen/mod.rs`; a `const` assertion keeps it so): a picture opens the share (`On`), an end item gives `NotFound` or `Unavailable`, and silence or a bad item is `Unavailable`. Later, `persephone_call_protocol::screen_frame::read_item` checks the share, format, size, stride and length of each item before it allocates; an end item ends the share (`Ended::Source`, `NotFound` or `Failed`), and a pipe that closes with no end item, or any bad item, is `Failed`. Pictures are 5 a second at most from the helper, and the session's own limiter still applies. On macOS the core names the display with `ScreenTarget::Display` (CoreGraphics display ID and size in points, version 12) and asks for the Screen Recording permission; the worker never asks, takes only the `SCDisplay` with that ID, and a different size or a missing ID is `NotFound`. `setCaptureMicrophone` exists from macOS 15 only: keep it behind `available!(macos = 15.0)`. Its Seatbelt additions are "to be measured on a Mac", and the backend was not compiled with the full worker or run on a Mac. Other targets use `screen/unsupported.rs` and report `Unavailable`. The Windows `windows` dependency keeps no graphics, Direct3D, DXGI, GDI, WinRT capture or DPI feature; add none back. The core names the screen (`ScreenTarget`); the worker never lists screens to the user and never takes another. The worker publishes one VP8 layer (`TrackSource::Screenshare`, screencast source, at most 1920x1080, 5 frames per second, 1.5 Mbit/s, no simulcast) and decodes at most one remote screen share on tile 5 at 1280x720 and 5 per second; more wait, and each member that shares shows as `ScreenSharer`. A screen start and stop reuse `CameraGate` (one open at a time, stale results dropped), and the own screen track gets the own key index before the first frame like the camera. There is no own screen preview.
- Other SFUs (ADR-0054): `Subscribe { index 1..=3, url, jwt }` opens one more `Room` as subscriber only. The connect runs on its own task (never awaited in the event loop) and its result returns through a bounded channel (`Connected`); `OtherEvents` is the one place that drains the rooms' event receivers, fairly, inside the single event loop. A secondary room never calls `publish_track`, never sets an own key index and never changes mute, camera or screen state; those use the main room only. Every participant, speaker, video and screen-share message carries the connection index (0 is the own SFU), and a remote video track is keyed by identity, track and connection. All rooms share one key provider (`RemoveParticipant` and `SetKey` go by identity). A secondary connect failure, a `Disconnected` event or a closed event queue sends `Connection { up: false }` and never ends the call; `mapping::Slots` uses each index once and never reopens it. `Leave`, `Eof` and every failure close every secondary room and stop connects that are still running (`close_others`). Do not log the URL or the JWT.
- Containment (ADR-0049): `containment/mod.rs` holds the bit constants and `missing_controls()`; one module per OS (`windows.rs`, `linux.rs`, `macos.rs`). Never change a released bit value. macOS (`containment/macos.rs`) applies the call Seatbelt profile with `sandbox_init` before any input and checks it; its service list is "to be measured on a Mac" and was not compiled or run on the development machine. Linux (`containment/linux.rs`) applies stage 1 before any input (non-dumpable, Landlock ABI 3 or newer, seccomp deny list; `clone3` returns `ENOSYS`) and `containment::apply_stage2()` after the audio connection and before `Room::connect` (no new `AF_UNIX` socket, no Landlock calls); a stage 2 failure ends the call with `Containment`. Keep the Landlock path table to the ADR; add no path without an ADR change. No path is writable without V4L2; `/dev/shm` is read only, because the file limit (256 MiB) is per file and a file there would outlive the worker.
- Windows default devices (ADR-0043 amendment of 2026-11-24): with no choice, `select_devices` opens the console default endpoints that `sound_defaults.rs` reads through MMDevice, when libwebrtc lists them (`mapping::system_default`). Never let it replace a chosen device: a missing choice stays `DeviceNotFound`.
- Linux microphones and speakers (ADR-0049): libwebrtc gives only `index:` IDs there. `pulse.rs` reads the sound server's sink and source names through `dlopen` of `libpulse.so.0` (one connection, at most 3 s, read only, no monitor sources in the lists) for `ListDevices` and, before stage 2, for a `Join` with a `pulse:` choice. `mapping::sound_path` decides: a `pulse:` choice needs the same name in `PULSE_SOURCE` or `PULSE_SINK` (else `Protocol`) and on the server now (else `DeviceNotFound`); then the worker leaves libwebrtc's device selection alone, and its default stream goes to that name. A name in the environment without a `pulse:` choice is `Protocol`. Keep this check: the sound server quietly falls back to its default for a missing name. Changes during a call (ADR-0049, amendment of 27 November 2026, proposed): `Join` opens `pulse::Session` (`open_pulse`) before stage 2, next to `sound_paths`, and the `Call` keeps it. It is one `pa_context` on a blocking `pa_mainloop`; every operation takes its lock on a `spawn_blocking` thread with a 3 s deadline, never in the event loop, and opens no socket or file, so stage 2 needs no change. `Session::switch` lists names, own streams and moves them: `mapping::own_streams` keeps only streams whose `application.process.id` is this process (the listing drops other programs' streams before its limit, `StreamList::keep`, so they never push the own ones out; the ID is the client's own word, which another client of the user could copy, a known limit in ADR-0049), each with the device name that the server shows (its sink or source index, resolved through the lists), and `mapping::plan_sound_move` checks both choices before either moves and plans from those routes (the worker caches no route). `pulse.rs` also reads monitor sources, keeps them apart (`Lists::monitors`) and uses them to name the route of a recording stream, so `undo` can put such a stream back; a monitor is never listed or chosen, but a start default may be one. A move that times out is `MoveOutcome::Unknown`, not a refusal: it is undone too, and `DeviceKept` needs the routes read again (`mapping::routes_kept`), else `AudioDevice`. New waiting targets are stored only when every immediate move worked. A kind with no own stream yet (no playback stream while nobody else is in the call) is not a failure: its target waits (`SoundTarget::Wait`, one per kind, a newer choice replaces it) and the change answers as done. The target waits also when it equals the device that a new stream would open on now: the server's default may change first, so the first try that sees the stream checks its route (a stream already on the target moves nothing, and the target ends). `Call::sound_trigger` (remote audio subscribed, own microphone published or unmuted, and a successful `SetDevices` that left a target waiting) starts tries at 250 ms, 1 s and 3 s (`SOUND_RETRIES`; no timer when nothing waits), and `Session::apply_pending(started, last, generation)` moves the target once a stream exists; a stream that is still not open after the tries reports nothing and keeps waiting until the next trigger. A try does the forward moves of both kinds first and the undo and route reads after, so one kind's rollback never uses up the other's forward time; the forward time is in three parts, the route read (`Deadlines::read`), the microphone's moves and the speaker's (`Deadlines::forward_for`), so a slow read or a slow microphone move never uses up a later step's time; the rollback reserve is in three parts too (the microphone's undo, the speaker's, `Deadlines::back_for`, then one route read for both), so every undo is sent before any route read. A try carries the generation of the newest change that the core was told worked (`SoundBook::generation`, which `Session::switch` gives at each commit; `session::tries_due`): a try that runs late after a newer change does nothing, so it never drops the newer target, and the targets of a change whose answer came too late (a timed-out `SetDevices`, answered `AudioDevice`) are never tried, so they never move a stream unasked. A failed move is noted by kind and the target stays, except at the last try, which drops it and sends an unasked `DevicesSet`: `DeviceKept`, or `AudioDevice` when a stream was lost, when the routes could not be read (the snapshot failed at the last try) when an earlier try left the kind's routes, or the other kind's, split (`Devices::lost`, set by a failed move that was not verified as undone, so it is never reported as kept; a kind with no stream in the last try keeps its mark), or when a try moved a stream of the other kind to its target or found one there that an earlier try left moved and not undone (`Devices::applied`: one route of the change moved, so the call does not run on the devices it had). A wait of the last try that times out sends `AudioDevice` (the outcome is not known). A change takes at most 5 s (`pulse::CHANGE_TIMEOUT`) counted from `started`, which the caller takes before `spawn_blocking` (`Session::switch(started, ..)` and `apply_pending(started, ..)`): a task that starts late or waits for the lock finds the deadlines passed and sends nothing. The forward moves use at most 3.5 s (`ROLLBACK_RESERVE` is for the undo), and no operation is sent after its deadline; each sound job (a change, or a try of the waiting targets) runs on a task of its own, one at a time (`session::SoundBook`), never in the event loop, so `Leave` and keys are served while the sound server is slow; the task waits `CHANGE_TIMEOUT + REPORT_GRACE` (250 ms) for the blocking thread and sends the result to the loop (`SoundDone`), so a task that keeps its deadlines is always heard and a timeout means that the blocking thread did not run in time (`AudioDevice`). A job is over only when its blocking thread ended: after a timeout the answer goes out, the task waits for the thread and then sends `SoundDone::Ended` (`session::end_late`), and no other sound job starts before that, so threads never run beside each other or add up while the sound server is slow. A `SetDevices` that comes while a job runs keeps its camera choice at once; its sound choice waits (the newest only), is decided against the accepted choice when the job ends, and is answered then; a try that comes due waits for the job too. Never move or touch a stream that does not name this process. The match by `application.process.id` is best effort, not proof of ownership: ADR-0049 records it as a security limitation that the owner accepted on 27 November 2026, so never describe it as an ownership check. A missing libpulse function or a failed connection means no session: the call goes on and a change answers `Unsupported`. `SoundBook::accepted` is the choice that the streams follow: the join's, then each accepted change; `None` after `AudioDevice`, a timeout, or a target that the last try dropped. A `SetDevices` with that choice (a camera-only change) is no sound change (`session::sound_route`), so it gives no sound error and never reaches the session; `session::run_change` runs a change through the `SoundSwitch` trait (`pulse::Session`, a fake in the tests); the join's choice after another accepted one is a real change, so the user can go back. A session whose defaults query failed answers every real change `Unsupported` at once (`Session::switch`), because "System default" cannot be resolved, so its accepted choice stays the join's. "System default" is the call-start default only while the server still has it (`mapping::pulse_target`, which looks up a start default also among the monitors). Results of a change on Linux: `DeviceNotFound` for an ID that is not `pulse:` or a name the server lacks; `Unsupported` when the session could not open, the defaults are unknown, or "System default" names a call-start device that the server no longer has; a kind with no own stream is no failure (it waits); `DeviceKept` when a failed move was undone and verified; `AudioDevice` when it was not, or the routes could not be read.
- Arguments (`args.rs`): Linux takes at most one `--camera=portal|v4l2|none` (none by default). Any other argument, or any argument on another OS, sets `CHECK_FAILED`, so the worker sends `Ready` and then `Failed(Containment)`. Read the mode with `camera::mode()`.
- Camera channel (`camera_channel.rs`, Linux): descriptor 3 carries one byte and one `SCM_RIGHTS` descriptor per message. The byte names the kind: `c` for a camera, `s` for a screen; a one-byte message of any other value closes the whole channel. Each kind keeps at most four pending descriptors in arrival order; one more of a kind closes that kind's descriptors and breaks it. Each `SetCamera { on: true, remote: true }` takes the oldest with the command (`camera::Grant::take()`) and moves it into its open, or drops it if the command opens nothing; the listing path takes one for `ListDevices`. `take_handle()` is the only reader. Keep the module free of other worker modules so it builds alone.
- Linux cameras (ADR-0049): `camera/linux.rs` dispatches by `camera::mode()`: `linux_portal.rs` (PipeWire over the descriptor from the core, `node.name` IDs, shared-memory buffers only) or `v4l2.rs` (raw ioctls; IDs join driver, card and `bus_info`, all required, so a different model in the same port is `NotFound`). `linux.rs` prefixes each ID with its path (`pipewire:` or `v4l2:`), so a choice from the other path or without a prefix is `NotFound`. `yuyv.rs` holds the format policy (NV12, I420, YUYV, at most 2560x1440 since ADR-0070, no MJPEG) and the YUYV conversion; `deliver_frame` hands YUYV on unconverted (`camera::Format::Yuyv`, Linux and tests only), and `fitted_i420` converts it after the frame admission and the rate limit, so a frame that the 15 fps limit drops is never converted. A refused portal never leads to V4L2, and a chosen camera that is absent is `NotFound`. `linux_portal::connect` is the only PipeWire entry (the screen share uses it too). It calls `webrtc::InitializePipeWire()` before `pw::init`: the static libwebrtc's weak `pw_*` stubs replace libpipewire's functions in the worker and stay null until then (a null call, SIGSEGV). Keep that call.
- macOS camera (`camera/macos.rs`, AVFoundation through `objc2`): `uniqueID` IDs, NV12 at most 1280x720, no fallback camera. A `NotDetermined` permission asks the user and waits at most 60 s (`OPEN_TIMEOUT` in `camera/mod.rs` is 65 s on macOS for this). A denied or restricted permission is `Unavailable`.
- A camera error never ends the call: report `CameraState`. A chosen camera that is absent is `NotFound`; never fall back to another camera. Turning the camera off revokes frame admission, stops and joins the capture thread (at most 3 s), then unpublishes the track. A capture that does not stop in time is kept and polled; no new camera opens while it runs, and the state is `Unavailable`, not `Off`.
- Every own track (microphone and camera) needs its frame cryptor set to the current own key index. `SetOwnKey` updates all of them. The camera sends no picture before that.
- Never await a camera open in the event loop. `begin_camera` opens on its own thread, and the result comes back through a bounded channel to `camera_opened`. `CameraGate` allows one open at a time, drops a stale result and releases its camera. An off and then an on during an open (the core's restart for a new device or quality) ends that open as `Completion::Restart`: `camera_opened` releases the old capture and calls `begin_camera` again, so the new open reads the current device and quality. An off with no later on ends it as `Cancelled`. `SetOwnKey`, `SetKey` and `Leave` are served while an open waits.
- Remote audio follows one `Playout` (deafened and volume, ADR-0055). Apply it to every subscribed remote audio track on every connection (the own room and each open room in `others`) when it changes, when another SFU's room opens, and to each new track in `TrackSubscribed`. Set the volume before enabling a track. Deafen never changes the microphone: the core sends `SetMuted` itself, before `SetDeafened(true)`.
- The level meters (ADR-0055, ADR-0059) read `get_stats` on the 100 ms tick, on their own task (`SoundProbe`, at most one, at most 500 ms, aborted at shutdown), never in the event loop. The own track is read first, then the remote tracks all at once (`read_all`), each by one 400 ms deadline (`SOUND_READ_BUDGET`); a read that misses it is `None` and its meter keeps its level, never silence. They read the own microphone track's `media-source` level for `SoundLevel`, and the subscribed remote audio tracks' inbound level for `ParticipantLevel`, the loudest track of each identity. They take the remote tracks from `Call::audio_roster` (`mapping::AudioRoster`: at most 128 kept in subscription order, the first 64 measured), which `on_event` and `other_lost` keep from the room events (audio `TrackSubscribed` and `TrackUnsubscribed` of every source, `ParticipantDisconnected`, `Disconnected`). No tick path calls `Room::remote_participants()`, which copies the SDK's whole participant map; the join listings call it once. `remote_audio` (the playout, on a change only) still lists every track, so deafen reaches each one. `mapping::LevelMeters` (one `LevelGate` each, at most `MAX_PARTICIPANTS`) sends a number when it changes, and a level above 0 again once a second (`SOUND_LEVEL_REPEAT`), so a page that attaches mid-call catches up. Silence is never repeated, except once for a participant that left.
- Remote microphone mutes (ADR-0059): send `ParticipantMuted` after each `ParticipantJoined` (`RoomChange::Joined` carries `microphone_on`), and when a remote microphone track is subscribed, muted, unmuted or unsubscribed. No microphone track counts as muted, so a participant that only listens or only shares a screen shows as muted.
- Device changes (ADR-0059): `SetDevices` goes through `switch_devices`. It never reads the system defaults in the event loop: `MediaDefaults::read` (a blocking COM query on Windows) runs once before the join, and "System default" during the call means the default when the call started. `resolve_devices` and `device_switch` check both devices before either changes, and `apply_switch` switches them and keeps `Call::sound_devices` naming the devices in use, also after a failure. A stored ID is not proof that the device works: `recording_lost` and `playout_lost` mark a device that a failed switch stopped, and the next change switches it again. A microphone switch counts only when capture runs after it. LiveKit 0.11 cannot start playout again, so a lost speaker stays lost: each later change answers `AudioDevice` and the user must rejoin. It answers `DevicesSet`. `SetDevices` also carries the camera choice, which the worker keeps for the next camera start (`camera_device`); on Linux without a `pulse::Session`, a sound choice equal to the join's (`joined_sound`) is no sound change. The rest of this bullet is for Windows and macOS. A missing selected device is `DeviceNotFound` and the call keeps its devices. A "System default" that names no listed device is `Unsupported` during a call. Linux does not use `switch_devices` or `Call::sound_devices`: `Call::change_devices` sends the change to `pulse::Session::switch` through `session::set_devices`, which keeps the camera choice whatever the sound answer; the Linux microphones and speakers bullet gives its results. `select_devices` is for the join only.
- Device tests (ADR-0059): `TestDevice` is a first message, like `ListDevices`; it connects to no server. `session::test_device` opens a sound test's device first (`sound_test::open`, off the runtime threads), then applies stage 2, then runs it (`Opened::run`, on its own thread). `sound_test.rs` listens (15 s, own level) or plays a 440 Hz tone (1.5 s). Windows: WASAPI in shared mode; `E_ACCESSDENIED` is `DeviceDenied`. Linux: one PulseAudio stream through the `libpulse.so.0` handle of `pulse.rs`, the default stream with no device name and `PA_STREAM_DONT_MOVE`; a `pulse:` choice is checked with `sound_paths` as for a `Join` and reaches the stream through `PULSE_SOURCE` or `PULSE_SINK`; any other chosen ID is `DeviceNotFound`; it must open before stage 2 (new socket); `PA_ERR_ACCESS` is `DeviceDenied`. macOS: a Core Audio HAL I/O procedure (32-bit float only) on the default device or the chosen UID; the device is found before the microphone permission is checked, so a missing device never prompts; a refused permission is `DeviceDenied`. Never request a permission in a default-run test on macOS: outside an app bundle it ends the process. The camera test takes the portal remote that the core sends before `TestDevice` (`Grant::take`), opens the camera as a call does and sends pictures on tile 0 for at most 30 s. `Leave` ends any test, which ends with `Left` or `Failed`.
- Microphone settings (ADR-0062): `Join` carries `auto_level` and `mic_gain`, and `SetMicrophone` changes them in a running call. `mapping::Microphone::new` is the worker's own check (a gain over 400 percent or off the step of 5 is `Protocol`; the protocol reader refuses it first). The gain goes to the voice engine's audio processing module through `native::capture_processing::set_capture_gain_percent` (a process-wide value that every live factory applies); the automatic level goes to the published microphone track through `RtcAudioTrack::set_auto_gain_control`. Both apply at once, and `apply_microphone` applies both again after each `SetDevices`. The device tests (`sound_test.rs`) do not use them. A refusal is noted, never fatal.
- Audio notes (ADR-0058 amendment of 2026-11-25): `note_audio` in `session.rs` writes `Note` records of the target `persephone::call_worker::audio` while the log is on: the devices at the join (counts and how each was chosen, never an ID or name), the microphone settings with what the audio processing module reports, and every 5 seconds the own level, the playout state and each remote audio track's packets, samples and level (`measure_levels`). Keep them to counts, flags and levels. Never add an identity, a device ID or name, a key or a token.
- Call statistics (ADR-0066): `session/stats_probe.rs` reads `get_stats` of the own microphone, camera and screen tracks and of one audio and one video track of each remote participant (at most `MAX_PARTICIPANTS`), only while the core has sent `SetStats { on: true }` (the Auto send quality also reads the own camera track through it with the statistics view off; see the camera send quality bullet, and keep that sampling when the view is off), at most once a second, on its own task with a deadline (`StatsProbe`; one read at a time, aborted at shutdown, a report of an older series is dropped by its number). It reads transports through those tracks, not through the room, because a `Room` is not clonable into the task. It never reads an address, port, candidate type, SSRC or codec. `mapping/stats.rs` is pure: `StatsBook` turns raw counters into rates from the change since each counter's sample before, over the time between the two reads, keyed by track ID or transport (a reset, a new track, a missing earlier value, a zero interval or a connection with an unread transport gives no rate, never a wrong one) and clamps every number to the protocol bound. Turning the statistics off and on keeps the one-second spacing of reads. The message goes to `Output::offer_stats`, which keeps at most one waiting reading (newest wins) and writes it after the control messages and the waiting picture of a round. Statistics never use the control queue.
- Video effects (ADR-0068, proposed): `effects.rs` (pure: no LiveKit, OS or I/O types) applies the background and then the colour filter to the I420 picture in `CameraFeed::frame`, after `fitted_i420` and before both the own tile and the SFU, so the others and the preview see the same picture; the camera test applies it the same way, and starts with the effect from `TestDevice` (`TestEffect::starting`), set before the camera opens and answered with `VideoEffect` then. A refused starting effect leaves the test without an effect (it shows the camera only on this device and sends nothing), unlike a `Join`, which keeps the camera off. `Planes::new` checks the sides (2 to 640, at most 640x360 pixels) and that each plane fits its stride; the scratch buffers (about 1.4 MB) are kept for the feed and never grow past that picture size. Blur and the pictures need the person mask from `segmenter.rs`. This build has none: `segmenter::available()` is `false`, `Devices` reports that, `SetVideoEffect` refuses such an effect and keeps the old one (`refused`), a `Join` that asks for one keeps the camera off (`CameraState::EffectUnavailable`), and a picture whose mask is missing or bad is dropped, never sent without its effect. Never fall back to sending the plain picture. The pictures are drawn from code; add no image files and no image decoding. The later segmenter (tract with an embedded MediaPipe model) needs its own owner approval for the download, provenance and SHA-256 check, licence and audit entries, per-OS cost measurement and a containment check, as ADR-0068 lists; it goes behind `Segmenter` with no change to the session, but it must add read-only accessors to `Planes` (size and planes) for the mask; keep the write access private. The effect reaches the capture thread through `SharedEffect` (one atomic word); the event loop is the only writer.
- Camera send quality (ADR-0070, proposed): `Join.video_quality` and `SetVideoQuality` give the most the own camera sends; no size crosses the wire and no answer exists. A new quality applies at the next `begin_camera`; a camera that is on keeps its tier, and the core restarts it. `send_tier.rs` (pure) holds the tiers, `SendTier { P360, P480, P720, P1080, P1440 }`, with boxes 640x360, 854x480, 1280x720, 1920x1080 and 2560x1440 (the sides swap for a tall picture) and VP8 bitrates 0.6, 0.9, 1.5, 2.5 and 4 Mbit/s at 15 frames per second. `P360` is only the Auto floor and the effect cap. A quality gives its tier (`Auto` the largest), and the camera's first picture caps that at the largest tier whose short side its short side reaches (`capped_by_capture`, `SendTier::reached_by`): a camera that opens at 1280x720 sends P720 at most, and a 640x480 camera reaches P480 and sends 640x480. A picture is never enlarged. The camera is opened for the top tier (`pick_capture_mode`). Speed comes first: the modes of at least 15 fps form the pool (an unknown speed, 0, counts; a known rate below 1 fps is 1, `video::whole_fps`; every mode when none is that fast), and sizes are compared only within it, so a 4K mode at 30 fps beats a 1080p mode at 5 fps. In the pool, a mode larger than 2560x1440 (either orientation) is left out while another mode of the pool remains; then the smallest fast mode that covers the tier's box wins, else the mode that reaches the highest tier up to the target by its short side (`SendTier::reached_by`), then the largest; a pool of only larger modes opens at its smallest. `CameraFeed::frame` scales to the tier in `SharedTier` (an atomic, set by the event loop only, read on every frame). While a video effect is not plain (`leaves_plain()` is false) the box is capped at 640x360, because `Planes` and the segmenter work at that size. The own preview is a copy scaled to the tile box when the sent picture is larger; it never passes the protocol limits. `publish_camera` gives the top tier's bitrate as `max_bitrate` (VP8, no simulcast, 15 frames per second). A first picture that comes after the open's 2-second wait (`FIRST_PICTURE_WAIT`) caps the tier when it comes (`cap_late_camera` on the event loop's tick; Auto through `AutoQuality::cap_top`); the published bitrate stays, because LiveKit has no call to change it after the publish. `send_quality.rs` (pure, no clock reads) is the Auto controller: it starts at P480 and takes one sample about every 2 seconds (`StatsProbe` with `set_auto`, own camera track only, even with the statistics view off; the core gets `Stats` only while the view is on). It reads the sending transport only (`RawStats::sending`: the publisher's, or the single transport of one peer connection), never a subscriber's round-trip time; the connections' numbers for the view take each value from any transport. Up one tier after 3 good samples in a row (available bandwidth at least the tier's bitrate, round-trip time at most 250 ms and at most 1.5 times the lowest of the run plus 50 ms) and `hold` since the last change; down one tier after 2 bad samples in a row (under 0.8 of the bitrate, or over 400 ms). `hold` is 10 s, doubles after a step down within 15 s of a step up (to 120 s) and resets after a tier that a step up gave holds 60 s. A missing value is neither good nor bad, and a sample with one makes no step in either direction. Linux raw capture takes sizes up to 2560x1440 (`yuyv.rs`); V4L2 reads the frame intervals to know each mode's speed and asks the driver for the chosen rate; the portal path only names the tier's box as the preferred size and cannot prefer 15 fps. macOS stays at most 1280x720 and tries the 1280x720 preset first from P720 up. Windows takes any listed mode through the picker, up to 2560x1440 while the speed pool has a mode of that size or smaller (it lists modes up to 3840x2160, MJPEG included). A tier change may be noted as the tier only (`note_camera`, never an ID or name).
- Pictures never use the control queue. `output.rs` keeps at most one waiting picture per tile (newest wins), and control messages always go out first. Pictures are RGBA in byte order R, G, B, A, at most 640x360 and 15 per second per camera tile, and at most 1280x720 and 5 per second on the screen tile (5), checked by tile index before allocation.

## Build

- The pinned libwebrtc must be verified first: `python tools/dev.py webrtc`. Set `LK_CUSTOM_WEBRTC` to the directory it prints for every cargo command. The build must never download libwebrtc.
- On Windows the prebuilt libwebrtc uses the static C runtime. Build and test this package with `RUSTFLAGS=-C target-feature=+crt-static`. `tools/dev.py` does this and builds the package apart from the rest of the workspace.
- On macOS, `build.rs` links the worker and its tests with `-ObjC`. Keep it: libwebrtc's Objective-C categories are dropped without it, and the first peer connection factory aborts. The `-ObjC` that webrtc-sys sets does not reach this package.
- `third_party/` holds vendored LiveKit crates with small marked patches (TLS 1.3 only and no proxy variables in `livekit-net`; key ring of 256 and a remote audio volume in `libwebrtc` and `webrtc-sys`; no built-in echo canceller in `webrtc-sys`, so capture never waits for playout; a microphone gain and automatic gain control in `libwebrtc` and `webrtc-sys`, ADR-0062). Read each `PERSEPHONE-PATCH.md`. They are patch sources, not workspace members.
