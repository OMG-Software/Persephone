# Key-holding core

This crate is the application entry process. ADR-0004 assigns sessions, SDK work, keys, stores, and the media broker to this process. The core runs real Matrix sessions through the SDK. The `--demo` view fixtures and demo events are synthetic; do not describe them as Matrix integration.

- Treat every UI request as hostile. Use the budgeted frame reader before body allocation, strict protocol decoding, and explicit argument validation.
- Keep bounded projections in `src/views.rs`. Preserve room, item, serialized-byte, name, body, and cursor limits. Truncate text on valid character boundaries.
- Keep identity normalization separate from message-body handling. Preserve the documented treatment of controls and bidirectional text.
- Keep room subscriptions bounded. Coalesce change notifications and fetch content through bounded calls. A slow UI must not create an unbounded event queue.
- Review lock order, wakeups, writer failure, pipe closure, and thread completion together when changing the serving loop. Do not infer full shutdown from a dropped handle or task status.
- Keep protocol violations fatal to the affected UI connection. Return bounded public error codes instead of internal diagnostics.
- Preserve UI process supervision and Windows Job ownership in `src/main.rs`, `src/ui_host.rs` and `src/platform/windows/ui.rs`. Unsupported platforms need measured equivalent controls before security claims.
- Keep per-OS code in `src/platform/<os>/` behind the traits in `vault.rs`, `credentials.rs`, `pick.rs`, `media.rs` and `ui_host.rs`. An OS without an implemented layer fails closed.
- Coordinate commands and events with `crates/core-protocol`, `src-tauri/src/core_link.rs`, the Tauri command surface, and frontend bridge.

- Screen sharing (ADR-0053, ADR-0064): the page asks with `call_screen { on }` and names no source. `calls/screen.rs` holds the `ScreenSource` trait; `platform/linux/screen_portal.rs` shows the core's warning window and runs the ScreenCast portal (no restore token, one source), keeps the portal session open for the share and closes it on stop, on any worker end state and with the call. On Windows and macOS the share's session in `ScreenControl` is a `WorkerStop` (`calls/controller.rs`), set under the control lock after the start is queued: closing it (the handle's stop, before `Off` shows) queues the worker's stop at once, and its `settled` flag keeps a stop from going twice or after the worker ended the share; a full queue leaves the stop to the call task's pending stop. The remote goes to the worker with the byte `s` directly before `SetScreen`. `platform/windows/screen.rs` is the Windows source: a message box per monitor (Yes shares, No shows the next, Cancel stops; No is the default) that lists monitors with the same rules as the worker and asks only about those within the call protocol's `screen_capture_size_ok`. The question numbers the offered monitors in list order ("Screen 2 of 2") and gives the size and the place (`whereabouts`: "main screen", the side of the main screen, and the order on that side when two or more offered monitors share it), and says how many it left out; the share's target is `ScreenTarget::Monitor` with the monitor's GDI device name (`MonitorName`) and size, never an index. `choose` reads the whole layout (`monitors().layout`: every monitor's device name, rectangle and mode) before the first box and again after a Share; `pick_unchanged` voids a Share given while it changed (`Cancelled`), because Windows can give a device name to another output after a change. The target also carries the monitor's `DesktopRect` from the second read; `monitors()` reads with per-monitor DPI awareness (physical pixels, as the worker) and puts the thread's own awareness back. A thread timer (`watch_cancel`) closes an open box within about 100 ms when the call ends; keep it, and take the quit message off the queue after the box returns. When the timer cannot start, `ask_with_timer` opens no box and answers Cancel. After the Yes and the layout check, `ScreenSource::capture` (`MonitorScreen::capture`, on the same blocking thread) starts the capture helper for the share (ADR-0067, proposed) through `platform/windows/screen_helper.rs` and the media broker, because Windows.Graphics.Capture is denied in the worker's container (`docs/evidence/screen-share-windows.md`); the worker never captures the screen on Windows. The pick gets the number the share will have (`screen_share + 1`); `screen_picked` refuses a helper of another number. `calls/screen_helper.rs` (`HelperShare`, plain `std`, tested on every OS with a fake) owns the helper: a waiter thread reports the exit (`state_for_exit`: stop `Off`, missing or changed monitor `NotFound`, a closed frame pipe and anything else `Unavailable`), `stop_and_join` closes the control pipe, waits `STOP_WAIT` (2 s), terminates the Job and joins the waiter, and dropping a share does the same on a reaper thread. Only one helper runs at once (`wait_until_idle` before a start). The helper's frame pipe goes into the worker with `CallWorkerLink::send_screen_frames` (`ScreenFrames`, then `SetScreen`); the core never reads frames and closes its copy. The call task keeps the helper in `screen_helper`; it ends with the share (stop, the worker's end state, the helper's own exit through `screen_ended_by_helper`), and `finish` joins it before the call and the session end go on; on Windows it also cancels and awaits a running pick (`end_screen_helpers`, at most 2 s); elsewhere the pick is cancelled but not awaited, and its task drops its grant, with any portal session, when it returns and waits until no reaped helper is active (at most 5 s). The pick holds a `LaunchGuard` from its last cancel check until the helper counts as active, so `helpers_active()` and the call's end include a launch under way; the launch and the helpers share one counter, so one read sees both. Keep both end waits bounded. The share's `WorkerStop` carries the helper's `HelperStop`: the handle's stop closes the helper's control pipe before `Off` shows, also on a full queue, and `exited()` never reports an end that was asked for. The start reserves both queue slots (`SCREEN_START_COMMANDS`) before the pipe goes into the worker, so a full queue fails only the share. On Windows the core's process starts hold the media broker's `process_start_lock()` (a test's start goes through `platform::windows::spawn_for_test`), except the `ShellExecuteW` link opener in `platform/windows/credentials.rs`, which does not take it (it is assumed to start processes without handle inheritance). A start that cannot take the pipe, or a missing or failing helper, leaves the share `Unavailable` and the call running; never fall back to capturing in the worker or the core. macOS (ADR-0064): `platform/macos/screen.rs` declares the CoreGraphics permission and display calls; `calls::screen::choose_display` checks `CGPreflightScreenCaptureAccess`, asks `CGRequestScreenCaptureAccess` once, then asks one Yes or No question for each display (main first) and sends `ScreenTarget::Display` with the display's CoreGraphics ID and size; a missing permission is `Refused`, and no display that the worker takes is `Unavailable` (nothing is asked). Never call it in a default-run test, because the request shows a system prompt. A cancelled or refused pick leaves the share off and never falls back to another source.
- Other SFUs (ADR-0054): `calls/other_sfu.rs` holds the pure rules (which SFU a member is on, at most 3 other SFUs, DNS host names only, the answer for each host). The core asks in its own window (`CallHost::confirm_other_sfu`, default "no") once for each host in each call, and only then requests one OpenID token and `/sfu/get` grant for that SFU with the profile's no-redirect client, and sends `Subscribe`. `View::accepts` takes a worker participant, speaker, share or video from connection `n` only when the member's membership names the SFU of `n`. A failed or ended other SFU only makes its members not reachable. Nothing is remembered after the call.
- Homeserver call tokens (ADR-0056): `calls/readiness.rs` reads the transports with its own requests (stable path, unstable path, then `.well-known`), not with the SDK's typed request. The two transports requests and the token request go through `bounded.rs`, which caps each answer while it is read and holds the only unknown-token refresh and retry rule (`room_relations.rs` uses it too); `Client::send` reads whole answers first. The `.well-known` fallback is read with `discovery::fetch`, under its ADR-0027 cap and with no token. A `wss` `url` transport gets its token from the homeserver's MSC4195 `get_token` (`calls/sfu.rs`). Its LiveKit identity is the hashed one. Keys find their member by `{user}:{device}` of the sender, and the core gives them to the worker under each backend identity of that member, again when those identities change. Such a transport is never another SFU.

- Join refusal and the alone rule (ADR-0063, proposed): `CallController::prepare` reads the room's power levels from the local store and answers `CallError::NotPermitted` (`join_error` `not_permitted`) with `can_send_member_state`, the function `readiness` uses, before the SFU discovery, the worker launch, the delayed event and the membership send. A 403 `M_FORBIDDEN` answer to the membership send is the same error (`membership_error`); any other refusal stays `Membership`. `LevelKey::JoinCalls` maps to the call membership event type in `room_settings::state_type`, so the one closed level change sets it. `calls/alone.rs` keeps the remote participants by connection from `ParticipantJoined` and `ParticipantLeft`, and drops a connection's participants on `Connection { up: false }`; the call loop ends the call with `EndReason::Alone` 30 s after `Connected` with nobody else, or after the last one left. At the deadline it first applies the worker's waiting messages (`alone_still_due`), so a join that waits unread keeps the call. The end uses the normal leave path. Keep the set bounded, and keep a call whose set overflowed. Its tests need tokio's `test-util` (dev-dependency only).
- Presence (ADR-0057, proposed): `presence.rs` holds the `Writer`, which picks every sync request's `set_presence` and the `PUT` of a changed setting, at most one write a second and a carried sync value at most every 15 seconds, the bounded `Book` of contacts' presence, and `Members`, the bounded book of the members the member panel last listed (`room_settings::readers` sets it). The contacts' two and the members' four lookups a round all run at once, so a round stays within one timeout. Never let a sync request use the SDK's default `online`: pass the writer's value to `account::sync_round`.
- Devices and levels (ADR-0059, proposed): `calls/device_test.rs` holds the pure test rules; `CallController::start_device_test` runs one test at a time on its own thread, refuses it while a call runs or joins (`in_call`), stops it when a join starts and ends it after `TEST_LIMIT`. The test worker starts with the `pulse:` name of the tested device only (`device_test::worker_audio`), and on the Linux portal path a camera test sends one portal remote before `TestDevice` (`devices::send_portal_remote`, cancelled by the user's stop). A stop recorded while the test worker starts ends the test before `TestDevice`, so no device opens; a later stop reaches the worker as `Leave`, which closes a device that opened. The test worker gets the diagnostic switch before `TestDevice` and on each change, and its records go to the log (`worker_record`, ADR-0058). A camera test's picture store is the controller's store only while no call runs. `Core::set_call_devices` also sends the microphone, speaker and camera choice to a running or joining call (`CallController::set_devices`, which sends `ToWorker::SetDevices`); the camera applies from the next camera start, and a failed microphone or speaker change is the status's `deviceChange`. Other devices' levels go to the hub as `SoundUpdate::Participants` and leave with the own level under its gap.
- Linux keyring (ADR-0061, proposed): `platform/linux/vault.rs` asks `confirm_keyring_creation` (default "no") only when `ReadAlias("default")` is `/` while a new secret is stored, at most once per open attempt, and only after a yes calls `CreateCollection` ("Login", alias `default`) reads the alias again after the answer (a default made meanwhile is used without `CreateCollection`, which would return it and could relabel it), and uses the collection it created (`created_collection`: the reply's path, or the prompt's result) only if that path was not in the provider's `Collections` list just before and the alias now names it. `store_new` owns the session-bus name `CREATION_NAME` (`CreationLock`) from its first search to its read-back, so no other core on that bus creates an item during the waits; do not move this lock to a file under a per-process directory. A core waits at most `CREATION_WAIT` (5 s) for the name, plus one `CREATION_CALL_TIMEOUT` (1 s) request that started before the end (the lock asks on its own connection with that reply timeout), because `main.rs` opens the profile before any window shows. Another core that still owns the name then is `VaultError::Busy` (`keyring_busy`); no session bus for the lock's connection is `VaultError::Missing(Missing::SessionBus)` (`no_session_bus`); any other lock failure, also a bus that exists but does not answer in time, is `VaultError::Failed` (`key_unreadable`). Never add `SetAlias`. A missing bus, provider, default keyring or display is `VaultError::Missing`, which `store.rs` maps to its own `StoreState`; never fall back to another collection, the kernel keyring, a file or the passphrase alone.
- Diagnostic log (ADR-0058, proposed): `diagnostics.rs` is the only writer. It is off at every start; `main.rs` erases the old file (overwrite, sync, truncate, delete) before the profile opens. Every string passes `diagnostics/redact.rs` before the writer thread gets it. `diagnostics/events.rs` writes event metadata only; content is always `[content]`. Request records use `Call::command()`, which reads only the command tag, never arguments. Never format a secret into a record, and keep the queue, line and file limits. Turning it on goes through `confirm_diagnostics` (default "no").
